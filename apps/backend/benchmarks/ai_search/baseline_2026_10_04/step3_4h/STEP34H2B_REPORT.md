# Step 3.4H.2b report: request-scoped latency contract (implemented, model-free)

Zero provider calls. Nothing pushed or deployed. Gate A, Gate B, retrieval ranking, provider order and reasoning settings are unchanged. H.3 (live-news cache) and H.4 (production-chain measurement) are not started.

## What was built
- `app/services/request_deadline.py`: one ABSOLUTE deadline per request in a ContextVar. `scope()` sets it (restores the previous value on exit, no token, so it is safe in an async generator), `usable()` is remaining minus the finalization reserve, `sub_budget()` is a nested earlier deadline that can never extend the parent or use its reserve. `AI_SEARCH_TOTAL_BUDGET_SECONDS=0` disables everything.
- Provisional settings (`app/core/config.py`, env-overridable; **starting values, H.4 may change any of them**): total 24, finalization reserve 2, classifier budget 3, minimum provider attempt 8, and a fifth value I had to add: **per-attempt cap 14**. Coupling rule: cap <= total - reserve - min attempt (= 14), otherwise the first attempt can consume the whole budget and no fallback is ever tried. The cap is what lets "provider 1 hangs, provider 2 still gets time" be true; it only applies inside a request deadline.
- `ai_service._call_with_fallback`: the seven hand-written tier loops are now one table-driven loop plus `_attempt()`. With no deadline active the behaviour is the old behaviour (verified: same models in the same order, same positional arguments including OpenRouter's extra headers, 99 existing provider-chain tests pass unchanged). With a deadline, `_attempt` refuses to start below the minimum usable time and otherwise runs the call under `asyncio.wait_for(min(cap, usable))`.
- Provider health semantics: a timeout where the attempt had its **full cap** is charged exactly like any provider timeout (30 s cooldown, `reason: timeout`). A cancel because the **request budget** ran out is logged `reason: deadline`, increments `deadline_cancels`, and does **not** touch provider exhaustion.
- Classifier: `_classify_market_pulse_llm` runs in `sub_budget(3 s)`. If it cannot answer in time the result is "" -> False -> the query is not treated as market pulse and takes the normal research route (the same outcome as any classifier failure; never a more permissive route). Its consumption comes out of the one shared deadline.
- Pipeline checkpoints (`_run_v3_steps`): (1) retrieval runs under `wait_for(usable - min attempt)`; a cut-off becomes a `retrieval_deadline_exceeded` response with internal `_retrieval_failures = {"deadline": "TimeoutError"}`, never "no evidence" and never an empty bundle through Gate A; (2) after Gate A, no specialist call starts if usable < min attempt; (3) if the provider chain stopped because of the budget the degraded reason is `deadline_exceeded`, not `capacity`; (4) if less than 0.25 s remains after generation, fail closed (no generated content is published without Gate B); (5) before assembly, if the deadline has already passed, fail closed.
- Public availability: `deadline_exceeded` and `retrieval_deadline_exceeded` map to `answer_availability.state = temporarily_unavailable` (the frontend keys on that state, so existing wording applies). Frontend wording for these two reasons was not separately reviewed.
- Routes: `/search` and `/search/v3` wrap `run_ai_search_v3` in `request_deadline.scope()`; `/search/stream` runs the step generator through `_bounded()`. Background callers never set it, so they behave as before.

## Verification
- `test_request_deadline_latency_contract.py`: 20 tests. They cover: no deadline = old behaviour and full-chain order; provider 1 hangs and provider 2 gets only what remains, with the request bounded by the usable window; insufficient budget prevents another provider from starting; full-allowance timeout is charged; early request-budget cancel is not charged; a real-HTTP trickling server cannot escape the attempt deadline (1 s httpx read timeout never fires, the 1.5 s attempt budget ends it, the connection closes); outer cancellation propagates and releases the tier slot; the classifier's slice shrinks the specialist's budget and never touches the reserve; retrieval cut-off is a retrieval failure; no specialist when time is short; Gate B still authorizes a generation that arrives inside the reserve; a generation with no time to authorize is never published; deadline vs capacity reasons; scope plumbing; background callers get no deadline.
- Mutation checks: removing the `wait_for` fails/hangs the hang and trickle tests; charging deadline cancels fails the poison test; removing the reserve fails 5; removing the minimum-attempt gate fails 1.
- AI Search + provider-chain selection: 773 passed, 1 skipped, 3 xfailed (live-engine tests excluded as before).

## Not done and debt
- `run_in_executor` work (valuation, VIX, enrichment, chart) cannot be cancelled; a slow one outlives a deadline and holds a thread. Not on this change's critical path; recorded in the 3.4H.2 design.
- Retrieval has no stage cap of its own beyond the request budget (that is H.3).
- `asyncio.wait_for` cancels a retrieval query mid-flight on the request's DB session; the route's session is closed afterwards and the response does not use it again. With a real network database (not exercised here) a cancelled in-flight query may need a rollback; to be checked when H.4 runs against the production database.
- Classifier chain journey: bounded, not removed. Whether the LLM classifier is worth its cost is an H.4 question (telemetry: classifier latency and fallback count).
- All five numbers are provisional.
