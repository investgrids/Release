## The contract (`schema.COMPOSITION_RULES`, appended once to every claim-bearing specialist prompt)
1. **Observations:** in `evidence.what_happened`, the most decision-relevant facts the listed evidence actually states, as separate factual sentences: usually 3-5, fewer when the evidence holds fewer, none when it holds none. Each is one fact from one or two listed items, copied exactly into `claim_sources` with those ids. The model chooses by informativeness for THIS question: concrete, quantified, dated or directional items over generic market commentary; when items point in different directions it includes both. The lists are ordered by relevance. It must not pad, repeat a fact in different words, or state something because it is typical of the topic.
2. **Synthesis:** `investment.summary` and `bottom_line` answer the question using only those observations: one or two hedged sentences (for example "mixed or incomplete"), with no new figure, date or event and no verdict, forecast, winner or recommendation. Observations are referred to in words, not numbers.
3. **Consistency in both directions:** every factual sentence must be listed in `claim_sources`; every `claim_sources` entry must be a sentence actually written in the answer; never list a claim you did not write, never write a fact you did not list. Gate B continues to enforce it; nothing is deleted after generation.
4. **Limits:** comparisons describe each side only as far as the evidence covers it and never name a winner; a single company reports what the evidence says, not an outlook it does not state; macro answers state a causal link only if a listed item states it; if the evidence cannot answer, say so briefly instead of filling space.
The schema field descriptions for `summary`, `bottom_line` and `what_happened` say the same thing. The contract names no expected fact and no topic-specific example (tested), sets no minimum count and forces no symmetry. The model chooses from visible ids, so the contract keeps working when live evidence changes.

## New finding (Gate B permissive gap; pinned, not fixed because Gate B is frozen this step)
A **year-less day-month date** ("8 October", "Oct 8") is not parsed as a date, and its lone digit is exempt as a single-digit number. So a date that exists only in a hidden summary and is written without a year is **not caught** (the same date with a year is caught). This is exactly the "October 8 results date" hazard you named. It is recorded as a strict `xfail` test (`test_a_year_less_date_from_a_hidden_summary_is_not_yet_caught`) so it cannot be forgotten. It needs its own narrow fix: parse day-month forms and require the month-day to appear in the model-visible text. Until then, the SR2 live result must be read for any year-less date claim.
